## 設計

1. **權重控制器（Python／JS 同一套規則）**：轉場由「層」組成（片段、起始時間、速度、遮罩）。在 t_s 切到新片段、時長 D 時，新層權重 w=(t−t_s)/D 線性上升，其餘各層由切換當下的權重按 (1−w) 等比下降，總和恆為 1。
   權重只由時間與切換紀錄決定，求值器不帶歷史狀態。不用 three.js `crossFadeTo`：它在淡化中途再次切換時，會把權重重設為 1／0，造成姿勢跳變。
2. **播放速度**：每層的片段時間以 speed 前進（action.timeScale），轉場時長 D 以實際秒數計。這樣三種速度在淡化期間取到的姿勢不同，比全域縮放的涵蓋面更大。
3. **姿勢混合**：Blender 端照 three.js `PropertyMixer` 的累加規則重做，依序以權重 `w/累計權重` 做 slerp 或 lerp，總權重小於 1 時再和原始值混合。runtime 端以真實 `AnimationMixer` 加上明確權重求值。
4. **上半身層**：遮罩為 `spine_01` 以上，包括脊椎、頸、頭、鎖骨、手臂、手指與劍。骨盆、腿與衣甲取自 Walk。
   片段依遮罩拆成上、下兩半；Walk 下半身權重恆為 1，Walk 上半身與 Cast 上半身依權重混合，避免總權重小於 1 時把腿拉回 rest。
5. **互動狀態**：各層狀態依權重加權平均（沿用既有混合取樣的做法）。劍的 socket 在接點須兩端一致（躺下→睡眠、睡眠→起床在床上，其餘在手上）。
6. **退出／進入時間**：
   - loop 來源取兩個相位，其中一個是腳在 stance 的時刻。
   - 非 loop 來源在結尾前 D·speed 開始淡化。
   - 目標片段從 0 開始。
   - 躺下→睡眠→起床依原設計的接點相接，姿勢已驗證 0 度／0 m。
7. **取樣**：每個（轉場、D、speed）以 120 fps 取樣淡化區間與前後各一步；60、30 fps 的取樣點都包含在內。
8. **Blender 轉場檢查**：新增 `scripts/cv1_transition_check.py`，沿用 clip check 的量測方法（`cv1_soup` 網格、r010 握持、劍對身體、腳底、床面支撐與淨空）。只對兩端「同時」都在時窗內的關卡套用時窗門檻。
   並輸出少量取樣的參考值，供 runtime 閉環使用：每個轉場取 200 ms、1x 的 25% 與 50% 兩點。
9. **runtime QA 頁**：新增 `p4.html` 與 `src/p4.js`，內容如下。
   - 載入一個角色 GLB 與其他片段的動畫。
   - 權重控制器與互動式控制：片段、轉場、速度、暫停／繼續／跳轉、修形開關、固定鏡頭。
   - 自動量測：與 Blender 參考值閉環比對（10 µm）。
   - 確定性：同一時刻分別經播放、暫停後繼續、跳轉三種方式到達，結果差須 ≤1e-9 m。
   - 迴圈接縫：以 LoopRepeat 跨過片段結尾。
   - 反覆切換：中途切換後的權重須連續且與無狀態求值相同。
   - 反例與耗時量測。
10. **待機銜接**：第三里程碑留下 LieDown／GetUp 和 Idle 端點的差異（右上臂 10.6 度）。若轉場關卡因此失敗，再在片段端改 IK 淡入；連續性關卡只看轉場起訖。

## 執行後的修正（2026-10-06，run-01 之後）

上列設計保留原文；以下是實際執行後改變或補充的部分。

- **Walk↔Run 退出相位**：改為兩端都在同一隻腳 stance 中點時切換（相位對齊），不再各自取相位。
- **continuity 判定**：依 r6 原文，淡化起點與「來源片段」、終點與「目標片段」比對。參考姿勢直接取自片段，不經權重與混合，所以會檢查到權重控制器與混合器本身。
  中途再切換時沒有單一來源片段，起點改和切換前一刻的姿勢比；被打斷的淡化沒有終點。四元數先正規化。
  run-01 用的是舊定義，結果以 `continuity-03/` 為準。
- **播放契約**：每步由控制器的整數步時鐘（t = k/fps，不累加）設定各動作的時間，再呼叫 `mixer.update(0)`。
  讓 mixer 自行累加時間時，時間會落在關鍵影格前後一點點。three.js 在剛好落在影格上時回傳 float32 原值，在影格前一點點時回傳正規化後的 slerp 結果，兩者差到 1.56e-8 m，超過確定性門檻。這條路徑只列為診斷，不列入判定。
- **互動狀態**：權重相加可能比 1 多一個浮點 ulp，混合後的狀態因此夾回 [0, 1]（Python／JS 雙實作與單元測試）。
- **反例**：都先在同一情境乾淨通過，再注入故障，並宣告預期失敗的關卡。
  - Blender 端：`walk-castupper-walk-r-b200-s1.0`，武器入手 → grasp，錯誤 stance 時窗 → feet_slide。
  - runtime 端：關閉修形 → 閉環，缺骨映射 → 閉環，three.js `crossFadeTo` 反覆切換 → 確定性。
- **診斷工具**：`--probe` 對單一取樣比較三種情況（混合、關閉修形、各片段單獨），只作診斷，不是結果。`--continuity-only` 只跑 continuity。轉場檢查會記錄所用模組的雜湊。
- **操作場景**：可選全部 164 個情境，載入時核對 `transitions.json` 的雜湊。
- **run-01 結果與待決事項**：見 `milestone-04-progress.json` 與 `p4-decisions-20261006.json`。
  - 腳滑：原地片段交叉淡化造成。
  - 床面：大衣的坐姿豁免在轉場中沒有延續。
  - 長而快的淡化跨過放劍／拿劍事件。
  - 皺褶區折疊。

## 使用者決定後的實作（2026-10-06，第 25 筆授權：A1 B1 C1 E 維持 F 同意）

- **A1 著地腳鎖定**（`scripts/cv1_foot_lock.py`、JS 雙實作 `src/cv1-foot-lock.js`、`tests/test_cv1_foot_lock.py`）：
  - 啟用條件：轉場淡化中（下半身有兩層以上），所有驅動雙腳的層都把該腳放在 stance 時窗內。
  - 鎖定期間：這隻腳釘在開始鎖定時的位置，再依混合後的名義速度往後帶（原地片段是地面在動）。用大腿、小腿兩段 IK 讓腳踝到位，腳掌保留混合後的世界旋轉。
  - 鎖定在 stance 持續時一直維持；任一層抬腳時，在 0.12 秒內放開（擺動期）。
  - 目標片段永遠不抬腳時（例如 Idle），在淡化結束時以 0.3 秒收步回到片段的腳位；收步抬高 min(4 cm, 水平偏移的一半)，量測紀錄抬高與移動距離。
  - 時間表只由事件與各片段的 stance 時窗決定；目標位置用時間表上幾個固定時刻的混合腳位計算。因此求值仍是時間的函數，runtime 端每次求值前把腿部骨架還原成 mixer 的值。
- **腳步判定**：stance 樣本若腳底最低點高於情境最低 stance 高度 5 mm 以上，就視為抬腳，中斷這段 run；收步本身因此不算滑動，另外記錄抬高與移動距離。
  另附「只依高度判定著地」的診斷值，不列入判定，揭露宣告 stance 以外、腳仍貼地時的移動。
- **continuity 判定**：轉場終點改為淡化結束與該淡化期間開始的腳鎖定放開兩者中較晚者；比較時排除劍（由 socket 判定）。

- **C1**（`scripts/cv1_p4_scenarios.py` → `transitions-02.json`）：進入淡化在目標片段第一個 socket／床面事件前完成，放不進去就縮短；離開非 loop 片段的淡化在最後一個事件後才開始。改動的 5 個組合列在 `fade_timing_changed`。

  - 跟 runtime 比對的參考點共 100 個（float32）：(100 ms, 1x)、(200 ms, 0.5x)、(200 ms, 1x)、(400 ms, 1.5x) 的淡化中點；(200 ms, 1x) 另加鎖定、放開、收步各段的中點、上半身層的回程淡化，以及反覆切換的 5 個點。
