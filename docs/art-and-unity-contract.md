# 首批遊戲客戶與選用 Unity 契約

本文件保存 EvoLoot、changshan-longdan 首批需求的美術與遊戲整合限制，以及未來選用 Unity 的驗收契約。通用核心依 `art-workflow.md`；此處的風格、面數與遊戲條件不是所有客戶的預設，不直接改動兩個遊戲或未建立的 Unity 專案。

## 需求欄位與建議預算

`schema_version: 1` 的清單列出 id、project、name、category、priority、demand、英文 prompt、target_triangles、texture_px、size_m、pivot、requires_rig、postprocess 和 sources。

- `priority` 的 0／1／2 是本次排程建議，不是服務佇列狀態或遊戲原承諾。先做容易重用且有用途的小道具／武器／環境；角色與大型建築完成後製前仍是候選。
- `source_backed` 只表示已有 source／資料／文件支持用途，3D 造型可仍是本次提案；`inferred` 是依用途推導的新需求；`reuse` 指已有資產先複核。本次 39 筆有 1 筆 reuse，不能把全部都轉成付費生成。
- `target_triangles` 是候選 LOD0 的建議三角形目標，`texture_px` 是每張主要貼圖邊長。服務的 targetpoly 參數與實際三角形不保證相等；生成、重拓樸或轉換後必須量測實際值。貼圖張數、材料數與 draw calls 仍需記錄。
- `size_m` 是 `[X,Y,Z]` 公尺包圍尺寸建議。尺寸來自 source 時會註明；其餘是本次產製起點。不是軟體自動驗證過的遊戲碰撞尺寸。尤其趙雲 reuse 不可依估值盲目縮放。
- `requires_rig: true` 表示綁骨或可驅動部位是遊戲使用前的要求，不代表生成結果已帶骨架。若沒有骨架、權重及動畫／程序 driver 的實證，就不能進入角色 runtime 或標為 game_ready。

| 用途 | 本次起點 | 理由與後續限制 |
|---|---|---|
| 單手劍、盾、長槍 | 約 1,200–2,600 三角形，1K 貼圖 | 保持握點及清楚輪廓；變體共享基礎幾何與材質，不能修改命中範圍 |
| 火盆、吊燈、箱子、殘骸 | 約 1,400–2,500 三角形，512／1K 貼圖 | 適合先驗證產製及導入；16 次火盆重用要共享材質／實例化 |
| 地牢模組 | 約 1,200–2,200 三角形，1K 貼圖 | 接合邊、尺寸與 pivot 比高頻細節優先，世界變體以材質及特效支持 |
| 300 兵場景角色 | 普通兵 4,000、隊長 5,500 三角形，1K 貼圖 | 是候選目標；仍需 LOD、骨架／材質共享、蒙皮批次或烘焙方案，未有性能 PASS |
| 單一重要角色／首領 | 約 7,000–15,000 三角形，1K／2K 貼圖 | 根據鏡頭距離和動作驗收；不可把主角預算複製到所有大量敵兵 |
| 建築／遠景 | 約 1,800–14,000 三角形，1K／2K 貼圖 | 單模板重用，控制材料數；大型主殿不得直接覆蓋集中碰撞配置 |

這些數值是本次建議；未經實際場景與硬體測量，不能寫成已改善 FPS、減少 draw calls 或達到任何平台性能門檻。

## 風格與可重用構造

EvoLoot 採原創風格化黑暗奇幻，武器人格必須透過刃形、色彩與可換飾件遠距辨識。清單雖有魔獸風格種族 enum 與借鑒文件，產製 prompt 不重現既有商業角色、特定首領或世界建築。五把劍保留共同握柄、長度、軸向與 socket；史萊姆家族優先共用主體，冰殼、刺、冠冕分離。

changshan-longdan 採風格化三國，現有程序兵的藍灰甲色、隊長深靛金甲與三叉紅長翎要保留可辨識差異。角色 A pose、空手，槍／劍／盾與披風／翎／飾件分離；不把服務生成的融合武器硬塞入持握 driver。城牆、門樓、兵營的模板重用必須回到 `src/world/layout.ts` 已有尺寸，而非把全城生成成一個不可編輯的大 mesh。

兩種美術風格可以共用 UV／PBR／尺度／證據流程，不能因此強制共用角色色盤或建築造型。shared 地牢套件只是潛在中立資源，不宣稱兩個遊戲已確定採用同一地牢。

## 尺度、pivot 與規則邊界

此批客戶的 Master 採公尺、+Y 為上，角色和生物預設面向 +Z；長武器主軸與握點由各項 pivot 描述約束，再由引擎 adapter 校準。若 exporter 或 importer 需要轉軸，在產物紀錄中寫出實際轉換，不靠任意旋轉／縮放掩蓋問題。源檔保留，修正作用在可回復的衍生檔。

角色使用雙足中點地面 pivot；道具使用底面中心，吊燈用懸掛點；門樓的高度基準與城牆分離。模組保留乾淨接合邊，組件與大場景分離。導入前量測實際 bounding box、套用 transform、法線與負尺度，不以 prompt 的公尺文字當驗證。

模型與材料只改外觀。不得由新 mesh 自動重建命中範圍、武器傷害／攻擊窗口、角色移速、root motion 或碰撞體；changshan 的 layout、招式、槍尖與刀光端點是獨立契約。骨架／武器軸改動要證明與既有 driver 一致，再進入遊戲整合任務。

## 中立交付與 Unity 匯入

先保留原始下載 GLB 和可追溯來源；衍生產物另存，不覆寫唯一 master。GLB 是中立容器，不表示 Unity 專案已可以直接使用。本次未確認任何 Unity importer 已安裝。

實際 Unity 整合時必須指定和記錄 Unity editor 版本、專案 render pipeline，以及明確的 glTF importer 套件／版本／選項。若改交 FBX，另記 exporter 版本、軸向／公尺轉換與材料搬移；FBX 也不是自動等價的 GLB 轉換驗收。本次不安裝 importer 或 Unity 套件。

材質以可檢查的 PBR 輸入為主，記錄 base color、normal、metallic／roughness 或打包貼圖的通道、alpha 和 emissive。檢查貼圖內嵌／相對路徑、色彩空間、UV、法線、材質索引與解碼器依賴。法線與非底色數據不能依視覺亮度隨意當 sRGB。HDR 火光、火焰、粒子及場景燈光由引擎配置，不把烘焙光效當 universal 材質。

人形角色在實際 Unity 專案再決定 Humanoid 或 Generic。Humanoid 需要對應骨架和 Avatar 驗證；Generic 需要各自的動畫／程序 driver。Hyper3D 產出有骨骼不等於已可 retarget；無骨架模型必須先完成骨架、權重、關節測試與 socket。非人形史萊姆／龍同樣需要明確的變形或部位驅動方案。

需求指定 Unity 時，驗收至少包括正確尺寸／朝向／pivot、材料呈現、動畫或 driver、指定 LOD、Collider 的獨立來源、prefab 可重複實例、資源引用完整，以及預期數量的場景性能。尚未驗收 Unity 不得宣稱 Unity 可用；獨立交付則依該需求的美術、技術與交付規格完成，不額外要求 Unity。

## 檢查狀態與證據

本 repo 的 offline GLB inventory 是局部檢查，只整理工具實際讀出的容器、三角形、材質、貼圖、骨架及動畫等資料；可提供的欄位以該次報告為準。它不驗證 UV 品質、法線正確性、真實公尺尺寸、pivot、蒙皮品質、材質呈現或 LOD 可用性。這些項目仍須後製實測與目標引擎驗收，inventory 成功不能等同完整技術驗收，也不能跳到 game_ready。

各階段獨立登記，不以一張渲染圖覆蓋缺口：

1. 需求已登記：有 source、版本、使用場景和唯一 id；核對已有資產與 reuse。
2. 生成已完成：服務 operation ID、參數、狀態與可用扣點證據；pending／unknown 不自動重新提交。
3. 已下載：本機檔案存在、大小、SHA-256、非秘密來源記錄；不保存 signed URL、key 或 cookies。
4. 已技術檢查：容器與依賴可讀，三角形、materials、textures、UV、法線、尺寸與 pivot 有數值；rig／動畫／LOD 分別註明已驗／缺少。
5. 已遊戲整合：在明確 repo／commit／分支接入，原有規則和碰撞有獨立驗證，實際 runtime 操作與圖像證據可追溯。
6. game_ready：該目標遊戲與引擎需要的所有驗收完成。只通過前四步、缺少需求指定骨架／LOD 或目標引擎未測，均不得跳到這個狀態。獨立資產的 delivered 與此目標遊戲狀態分開，不強制每件資產進遊戲。

`cl-zhaoyun-reuse` 的文件記錄是 21 骨、無獨立動畫 clip、僅 LOD0，且存在於 e00 工作樹。先複核 source／hash／adapter，禁止再次送生成；專用21骨 adapter不能推廣成通用角色自動綁骨。文件歷史通關／測試不能替代本次復驗。

## 月訂額度的批次策略

目標是每月把已授權月訂額度盡可能轉為有用途的模型。先從一件重複使用的小道具建立下載、技術驗收與整合樣本，再把更多同類需求分批；角色必須預留後製和驗收能力。失敗或品質不足要先分類與檢查原 operation，不能為消耗點數無條件重送。

付費提交前以服務即時結果核對月訂與普通點數分項、重置週期及剩餘額度；API總餘額不能替代月訂證據。只使用已明確授權的月訂範圍，普通點數、加購、升級不在本契約預設範圍。沒有實際餘額、單次價格和重置日期證據時，不預設「每月能生成多少件」或「本月一定耗盡」。

每批先複核 catalog／sources／已有模型，保存唯一 operation ID、參數、預算與狀態，再送出；完成下載和QA之後才決定下一批是否需要調整。未經過使用者明確排程授權，不建立自動月任務、無人值守消費或月底自動補扣。產製過程保留下一次繼續所需的 pending 狀態，不以新的 operation 重置未知結果。

目前契約只定義需求與驗收路徑，未改變遊戲規則，未證明任何生成結果 game_ready，未完成 Unity 接入。後續遊戲整合、外部發布或排程需要對應具體授權與獨立驗證。
